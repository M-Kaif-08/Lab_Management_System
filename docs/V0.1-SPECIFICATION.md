# v0.1: Single-lab foundation

**Updated:** 2026-11-07  
**Status:** Planned implementation milestone.

## Outcome

A fresh independent installation can be initialized, its administrator can log in, manage staff and lab settings, and staff can log out. The same application runs in local and VPS configurations. Clinical workflows follow in later milestones.

## Deliverables

1. Scaffold the workspace described in [Architecture](ARCHITECTURE.md), with configuration validation and documented commands.
2. Implement the finalized foundation tables in the [v0.1 schema](database/V0.1.md), restricted runtime credentials and versioned migrations. Use its column definitions, constraints, indexes and transaction rules as the v0.1 database contract. Later additions are indexed in the [complete schema](DATABASE-SCHEMA.md).
3. Implement secure bootstrap, local staff setup/recovery, sessions, roles and required audit events.
4. Add login, required password change, foundation dashboard, staff management and lab settings screens. The dashboard shows lab identity/user roles until real operational modules exist.
5. Add initial Docker Compose/proxy configuration, persistent volumes, health checks and synthetic seed data.
6. Record acceptance commands/results and unresolved defects.

## Account setup and recovery

Use a server-local maintenance command to create the initial administrator, prompting for the password without logging it. Refuse to bootstrap over an initialized installation. Provide no public registration or default password.

Offline-capable staff flow: an administrator creates a user and obtains a short-lived, single-use setup link through a restricted, audited screen for direct delivery. Password setup is required before normal access. Links use the configured origin, keep secrets out of access logs and browser history, and expire after an initial configurable 24 hours.

For recovery, an administrator may issue an audited reset link after verifying the staff member's identity; initially expire after 30 minutes. A controlled server-local command handles loss of administrator access. It requires authorized server access, records the action and invalidates old sessions/tokens. Email delivery is optional and must not be required locally.

Never record raw links/tokens in audit logs. Store token digests and consume atomically; reject expired or replayed tokens. Administrative link delivery is sensitive and must be permission-checked.

## Authentication and authorization

Staff sign in with a normalized unique login name; email is optional contact information. Accounts use invited, active and disabled statuses. Setup activates invited accounts; disabled accounts cannot log in or redeem tokens. Follow the schema's authentication-version and row-version rules for account changes. Keep at least one active administrator with a password and no forced-password-change restriction.

- Hash passwords with Argon2id; benchmark parameters during implementation. Allow password-manager paste and long passphrases.
- Use random opaque session tokens and store digests server-side. Production cookies are host-only, Secure, HttpOnly and SameSite=Lax.
- Enforce idle/absolute expiry, logout revocation and current authentication version on every authenticated request. Initial configurable limits: 30 minutes idle, 12 hours absolute.
- Require session-bound CSRF protection and configured-origin checks for mutations; protect login and setup/reset submissions from cross-origin abuse.
- Rate-limit authentication and use generic credential/recovery errors.
- Enforce roles in APIs. Serialize changes to protect the last active administrator; revoke access after password, role or status changes.
- Validate payloads, use safe database queries, paginate lists and return safe errors without secrets.
- Keep private responses out of shared caches.

## Foundation API groups

| Group | Responsibility |
| --- | --- |
| /api/auth | Login, logout, current session, setup/reset completion and required password change |
| /api/users | Authorized staff creation, listing, role/status updates and setup/reset issuance |
| /api/settings | Authorized lab profile/settings access and updates |
| /api/dashboard | Current lab and staff identity |
| /api/health/live | Process liveness without infrastructure details |
| /api/health/ready | Database/migration readiness; generic unavailable response on failure |

Finalize endpoint request/response contracts before coding. Separate public login branding from protected settings so contact/infrastructure details are not inadvertently exposed.

## Acceptance checklist

- [ ] Fresh setup creates exactly one lab profile and a usable administrator; repeated bootstrap is safely refused.
- [ ] Migrations are repeatable, checksummed and locked; drift or failed migrations block readiness.
- [ ] Local login, setup and reset work with internet disconnected.
- [ ] Expired/replayed setup/reset links fail; concurrent redemption has one winner.
- [ ] Unauthorized direct API calls and role escalation attempts fail.
- [ ] Concurrent administrator removal cannot remove the last active administrator.
- [ ] Logout, expiry, role/password changes and deactivation invalidate access.
- [ ] HTTPS cookie behavior, CSRF/origin validation and authentication throttling are verified.
- [ ] Required changes and audits succeed or fail together; logs contain no credentials/tokens.
- [ ] Runtime database credentials cannot migrate, alter audits or access another installation.
- [ ] Database failure returns bounded safe errors; no fallback database is used.
- [ ] Two independent Compose installations use the same release with separate settings, records, sessions and storage.
- [ ] Browser smoke flow covers setup/login, staff changes and logout.

Use PostgreSQL integration tests and API tests for the security and concurrency rules, plus a small browser smoke flow. v0.1 is a foundation milestone, not permission for clinical use.

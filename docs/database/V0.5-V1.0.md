# v0.5 and v1.0 — Administration and operational readiness

**Status:** Implementation design; no migrations, views or recovery checks have run.

## v0.5 schema changes

Extend lab_settings with explicit policy columns. These are engineering defaults requiring lab confirmation before clinical use.

| Column | Type/default | Constraint and use |
| --- | --- | --- |
| allow_self_review | boolean DEFAULT false NOT NULL | Whether an entering reviewer may approve their own result set |
| allow_partial_reports | boolean DEFAULT true NOT NULL | Whether approved subsets may be released while other tests remain pending |
| require_full_payment_for_delivery | boolean DEFAULT false NOT NULL | Whether routine patient delivery requires outstanding=0; never changes clinical approval |
| policies_confirmed_at | timestamptz, nullable | Confirmation marker |
| policies_confirmed_by | uuid, nullable FK users(id) | Active lab admin at confirmation |

Confirmation fields are both NULL or both present. Policy updates clear confirmation unless the update is explicitly reconfirmed by an administrator, require expected settings row_version and audit actor/reason. Existing installation rows receive the defaults with confirmation NULL; the pilot gate blocks until reviewed.

v0.3/v0.4 enforce these same baseline values through typed deployment configuration before v0.5 adds the columns. The v0.5 migration explicitly copies the effective configured values into settings and removes those configuration overrides only after verification. No deployment may silently change policy during upgrade. Runtime uses one policy source per version.

The full-payment setting applies to routine patient download/printing by delivery staff; authorized reviewers must retain access for review and corrections. Defer any additional exception mechanism until specified. Earlier released reports are preserved even if policy changes.

No new administrative domain tables are required. Reuse users, user_roles, user_permissions, lab_settings and audit_events. Backups, provider subscriptions and sales are not lab domain tables.

## Dashboard and reporting views

Create ordinary SQL views or parameterized queries, never duplicate mutable summary tables:

| View/query | Definition |
| --- | --- |
| order_progress | Uncancelled test items, their latest submitted/approved revisions and latest released report coverage; distinguish approved from delivered/released |
| invoice_balances | The v0.4 formulas for adjusted total, net paid, outstanding and refund_due; void invoices contribute zero |
| daily_collections | Payments grouped by event date in lab timezone, returns separately, and net movement |
| work_queue | Pending collection, received work, submitted-for-review and approved-awaiting-release |
| audit_search | Bounded filters by actor, target, action, outcome and time |

Aggregate each financial child table separately before joining to avoid multiplying payments by adjustments. Compute the latest approved revision and latest released report content explicitly. A released older revision does not count as release of a newly approved amendment. Date filters convert local start/end to UTC and use half-open intervals. Financial summaries use payment/return event dates and show capture dates separately when relevant.

Runtime views must not bypass API role/field permissions. Receptionists cannot obtain unrestricted financial or audit exports through dashboard queries. Add indexes only after checking real query plans against the agreed workload.

## v1.0 database and operational gate

No new business tables are planned for v1.0. It validates the cumulative v0.1–v0.5 schema and may add evidence-driven indexes through versioned migrations.

Required evidence:
- Fresh install of all migrations and stepwise upgrade from each earlier version with synthetic historical data.
- Catalog, patient and lab changes leave approved result snapshots, issued invoices and released report files intact.
- Checksums/foreign keys/constraints/roles match the documented design.
- Backup manifest includes installation UUID, application version, migration versions/checksums, backup time and referenced file checksums; secrets and keys remain protected separately.
- Restore database and files to an isolated server, verify numbering counters, permissions, balances, report versions and file hashes; revoke restored sessions/tokens before opening staff access.
- Rehearse interrupted upgrade, file publication and local-to-VPS cutover with one writable source at a time.
- Measure acceptable data loss and recovery time against agreed client targets.
- Validate disconnected local operation, shared-VPS installation isolation, HTTPS and workload performance.
- Confirm clinical policies, report templates and retention responsibilities with the pilot lab.

Operational backup/release manifests are files maintained by deployment tooling, not editable lab records. Keep measured results in release evidence; do not mark this gate complete from documentation alone.

## Migration sequence

| Milestone | Planned migration groups |
| --- | --- |
| v0.1 | Foundation tables, constraints, triggers, indexes and runtime grants |
| v0.2 | Numbering, patients, catalog, ordered snapshots and specimens |
| v0.3 | Results/reviews/files/reports; migrate logo key to file reference in verified steps |
| v0.4 | Explicit financial permissions, immutable billing ledger, receipts and idempotency |
| v0.5 | Copy effective policy configuration into settings; administrative views/indexes |
| v1.0 | Only measured operational/index fixes, followed by full upgrade/restore validation |

Application version and migration version are separate. A release can contain multiple ordered migrations. Never edit a migration already applied to a customer installation; create a new one and document recovery.

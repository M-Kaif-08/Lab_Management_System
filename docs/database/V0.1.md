# Database schema — v0.1

**Updated:** 2026-11-07  
**Status:** Finalized design for v0.1 implementation. No migrations have been created or database tests passed.

Each customer installation has one PostgreSQL database and one lab profile. Local and VPS deployments use the same seven foundation tables. The cumulative schema and later releases are indexed in the [database overview](../DATABASE-SCHEMA.md).

## Conventions

- Every column is NOT NULL unless marked nullable. A dash in Default means no default.
- UUID identifiers are generated by trusted application/maintenance code. Timestamps use timestamptz; display in the lab timezone.
- All foreign keys use ON DELETE RESTRICT and ON UPDATE RESTRICT.
- Required text is trimmed and nonempty; optional text is NULL or trimmed/nonempty. Limits use char_length. Reject overlong input without truncation.
- Use text with CHECK constraints for fixed statuses/roles.
- Mutable created_at values are immutable. BEFORE UPDATE triggers set updated_at, increment row_version where present, and reject identity changes.
- Use the public schema with PUBLIC CREATE revoked. Secrets, database credentials, public origins and filesystem roots belong in deployment configuration.
- Check constraints compare stored values, not current time. Expired sessions/tokens remain valid stored rows until cleanup.

## 1. lab_settings

| Column | Type | Default | Constraints |
| --- | --- | --- | --- |
| id | smallint | 1 | PK; CHECK id = 1 |
| installation_id | uuid | — | UNIQUE; immutable |
| display_name | text | — | 1–200 characters |
| timezone | text | 'Asia/Karachi' | 1–100 characters |
| currency_code | text | 'PKR' | Matches ^[A-Z]{3}$ |
| contact_phone | text, nullable | NULL | Maximum 40 characters |
| contact_email | text, nullable | NULL | Maximum 254 characters |
| address | text, nullable | NULL | Maximum 1000 characters |
| logo_file_key | text, nullable | NULL | Maximum 255 characters; opaque storage key |
| report_footer | text, nullable | NULL | Maximum 1000 characters; plain text |
| receipt_footer | text, nullable | NULL | Maximum 1000 characters; plain text |
| row_version | bigint | 1 | > 0; increment on update |
| created_at | timestamptz | CURRENT_TIMESTAMP | Immutable |
| updated_at | timestamptz | CURRENT_TIMESTAMP | Set by update trigger |

The singleton PK allows at most one row. Bootstrap creates it with the initial administrator in one transaction; readiness requires it. Reject changes to id/installation_id. Settings updates supply expected row_version and reject stale changes.

Validate timezone against supported IANA names and currency against supported codes in application code. Validate email format there as well. Resolve logo_file_key under the configured storage root after ownership/type/size checks; never accept an arbitrary path or external URL. Retain installation_id during a hosting move; generate a new one for a new customer.

## 2. users

| Column | Type | Default | Constraints |
| --- | --- | --- | --- |
| id | uuid | — | PK; immutable |
| login_name | text | — | UNIQUE; matches ^[a-z0-9][a-z0-9._-]{2,63}$; immutable |
| display_name | text | — | 1–200 characters |
| email | text, nullable | NULL | Maximum 254 characters; contact only, not unique |
| password_hash | text, nullable | NULL | Argon2id encoded hash; maximum 1024 characters |
| status | text | 'invited' | invited, active or disabled |
| must_change_password | boolean | false | True requires a non-null hash |
| auth_version | bigint | 1 | > 0 |
| row_version | bigint | 1 | > 0; increment on update |
| created_at | timestamptz | CURRENT_TIMESTAMP | Immutable |
| updated_at | timestamptz | CURRENT_TIMESTAMP | Set by update trigger |

Normalize login names with trimming and ASCII lowercasing before validation. Email is optional and is not a login identifier. API validates its syntax.

CHECK active implies a non-null password_hash; invited implies a null password_hash; must_change_password implies a non-null hash. A non-null hash must start with the Argon2id encoded prefix and be nonempty; the password service validates full encoding and parameters.

Invited users cannot log in. Setup assigns a hash and changes invited to active. Disabled users cannot log in or redeem tokens. Re-enabling returns an account with a hash to active, or without a hash to invited; require a new setup link when needed. Old sessions/tokens never become valid again.

A forced-password-change login is restricted to change-password, session inspection and logout; operational access is denied until the password changes. Profile edits use expected row_version. Security changes also increment auth_version; role changes update the associated user row.

## 3. user_roles

| Column | Type | Default | Constraints |
| --- | --- | --- | --- |
| user_id | uuid | — | FK users(id) |
| role | text | — | lab_admin, receptionist, technician, reviewer or cashier |
| created_at | timestamptz | CURRENT_TIMESTAMP | Immutable |

Composite PK (user_id, role). Multiple roles are allowed. A role replacement removes/inserts rows transactionally. Retain at least one role per user through transaction checks. Administration alone does not confer clinical approval. The last-active-admin rule is specified under transactions; a row CHECK cannot enforce it.

## 4. sessions

| Column | Type | Default | Constraints |
| --- | --- | --- | --- |
| id | uuid | — | PK; internal identifier, not authentication secret |
| token_digest | bytea | — | UNIQUE; octet_length = 32 |
| csrf_token_digest | bytea | — | octet_length = 32 |
| user_id | uuid | — | FK users(id) |
| auth_version | bigint | — | > 0; snapshot of user version |
| created_at | timestamptz | CURRENT_TIMESTAMP | Immutable |
| last_seen_at | timestamptz | CURRENT_TIMESTAMP | >= created_at |
| idle_expires_at | timestamptz | — | > last_seen_at |
| absolute_expires_at | timestamptz | — | >= idle_expires_at |
| revoked_at | timestamptz, nullable | NULL | NULL or >= created_at |

Generate independent session/CSRF secrets using at least 32 random bytes; store SHA-256 digests only. Require active user status, matching auth_version, no revocation and both expiries in the future on authenticated requests. Extend idle expiry only for a currently valid session and never beyond absolute expiry. Initial configurable durations: 30 minutes idle, 12 hours absolute.

The client obtains a raw CSRF secret through authenticated same-origin responses. After reload, issue a replacement CSRF secret and digest; clients refresh/retry on stale CSRF rejection. Digests cannot recover the raw secret. Session-token rotation is independent of CSRF retrieval. Never log either secret.

## 5. account_tokens

| Column | Type | Default | Constraints |
| --- | --- | --- | --- |
| id | uuid | — | PK |
| token_digest | bytea | — | UNIQUE; octet_length = 32 |
| user_id | uuid | — | FK users(id) |
| purpose | text | — | activate or reset |
| auth_version | bigint | — | > 0; snapshot at issuance |
| created_at | timestamptz | CURRENT_TIMESTAMP | Immutable |
| expires_at | timestamptz | — | > created_at |
| consumed_at | timestamptz, nullable | NULL | NULL or >= created_at |
| revoked_at | timestamptz, nullable | NULL | NULL or >= created_at |

CHECK consumed_at and revoked_at cannot both be non-null. Create a partial UNIQUE index on (user_id, purpose) WHERE consumed_at IS NULL AND revoked_at IS NULL. Expired unclosed rows also occupy this index: revoke them before inserting a replacement, in the same transaction.

Use at least 32 random secret bytes and SHA-256 digests. Configurable initial lifetimes: activation 24 hours, reset 30 minutes. Activation requires invited status; reset requires active status. Both require current auth_version, unexpired time and neither terminal marker. Disabled accounts, replay and wrong purposes fail generically.

Token links use configured origins and URL fragments; completion submits secrets in POST bodies. Keep secrets out of logs/history. Direct administrator delivery works without email.

## 6. audit_events

| Column | Type | Default | Constraints |
| --- | --- | --- | --- |
| id | uuid | — | PK |
| actor_kind | text | — | staff, system or anonymous |
| actor_user_id | uuid, nullable | NULL | FK users(id) |
| action | text | — | 1–100 characters; allowlisted action |
| target_type | text, nullable | NULL | Maximum 100 characters |
| target_id | uuid, nullable | NULL | Historical identifier; no polymorphic FK |
| outcome | text | — | success, denied or failure |
| reason_code | text, nullable | NULL | Maximum 100 characters; allowlisted code |
| request_id | uuid | — | Server/maintenance-generated correlation ID |
| metadata | jsonb | '{}'::jsonb | CHECK jsonb_typeof(metadata) = 'object' |
| created_at | timestamptz | CURRENT_TIMESTAMP | Immutable |

CHECK actor_user_id is present exactly when actor_kind = staff. CHECK target_type and target_id are both NULL or both present. Use installation_id as the UUID target for settings. Unknown login attempts use an anonymous actor, not an invalid user FK.

Application code allowlists metadata per action. Exclude passwords, tokens, connection credentials and unnecessary medical content. Runtime may SELECT/INSERT audit rows for permission-checked application flows but cannot UPDATE, DELETE or TRUNCATE them. Database ownership is a separate maintenance trust boundary.

## 7. schema_migrations

| Column | Type | Default | Constraints |
| --- | --- | --- | --- |
| version | text | — | PK; 1–100 characters |
| checksum | bytea | — | octet_length = 32; SHA-256 of migration file |
| applied_at | timestamptz | CURRENT_TIMESTAMP | Immutable |

Use ordered migration filenames such as 0001_foundation.sql. Maintenance credentials acquire a database-scoped advisory lock, verify existing checksums and apply each foundation migration and ledger entry atomically. Record only successful migrations. Failures belong in maintenance diagnostics. Missing required migrations or checksum drift block readiness.

## Relationships and indexes

Users have many roles, sessions, tokens and staff audit events. The settings row describes the whole installation; no per-record lab_id is required.

Primary keys and UNIQUE constraints already supply indexes. Add:

| Table | Additional indexes |
| --- | --- |
| users | (created_at DESC, id DESC) for staff pagination |
| user_roles | (role, user_id) for role/admin lookup |
| sessions | (user_id), (idle_expires_at), (absolute_expires_at) |
| account_tokens | Open-token partial UNIQUE above; (user_id), (expires_at) |
| audit_events | (created_at DESC, id DESC); (actor_user_id, created_at DESC, id DESC); (target_type, target_id, created_at DESC, id DESC) |

Use bounded timestamp/UUID pagination. Add query-specific search indexes only when justified. Never put current-time expressions into partial-index predicates.

## Required transactions and locking

All relevant paths follow lock order: settings singleton, then user rows in ascending UUID order, then token/session rows. Operations not needing settings may start with user rows but must not acquire settings afterward. Recheck eligibility after locks; do not trust earlier middleware checks alone.

1. **Bootstrap:** Take a dedicated database advisory transaction lock. Verify settings/users are empty. Insert settings, an active administrator with a hash, admin role and success audit atomically. Reject partial existing initialization for maintenance investigation. No default password or public bootstrap endpoint.
2. **Staff/security changes:** Lock settings FOR UPDATE and the acting/affected users in UUID order. Recheck actor authorization. Apply changes, require at least one role per affected user and at least one active administrator with a password and no forced-password-change restriction. Increment affected auth_version for role/password/status changes; revoke sessions and unconsumed tokens; audit before commit. Reject changes that remove the final usable admin. Profile-only edits need row_version updates but not session revocation.
3. **Token issuance:** Use the same settings/user lock order and verify actor/target eligibility. Revoke existing open tokens of that purpose, insert the token with current auth_version and audit atomically. Return the raw link once after commit. Lost delivery uses reissue. Issuance alone does not invalidate an active account's password/sessions.
4. **Redemption:** Resolve the candidate user from the digest; then lock settings, user and token and re-read all state. Verify purpose/version/expiry, conditionally consume exactly one row, set the password, activate if appropriate, clear must_change_password, increment auth_version, revoke other tokens/all prior sessions and audit atomically. Return to normal login. Concurrent replay has one winner.
5. **Login:** Check the hash, lock the user and recheck status/hash/auth_version before creating the session and success audit in one transaction. A concurrent password/status change must prevent a stale login. Failure audits use a separate safe transaction; do not issue a session when the success audit cannot commit.
6. **Protected mutations:** Lock the actor user and recheck session/version/expiry and permissions before business writes. If settings is needed, lock it first. This orders security revocation against mutations. Business updates and required audits commit together.

Hash computation may happen before locks; its source state must be verified again inside the transaction. Cross-table admin/role rules belong in transaction services and concurrency tests, not impossible row CHECK constraints. Maintenance writes must honor the same invariants.

## Privileges and retention

Use a non-login schema owner, separate controlled migration credentials and an installation-specific runtime role. Runtime has no superuser, database/role creation, schema creation or migration-writing rights. Revoke inappropriate PUBLIC CONNECT/schema privileges and grant access only to the installation database.

Grant only required table/column operations: runtime cannot delete users/settings, alter immutable identifiers, or modify audit history. Protect immutable values with triggers/column grants. Migration ledger is read-only at runtime. Bootstrap/recovery commands use controlled server access and audited transactions.

A maintenance cleanup job removes sessions after expiry/revocation and tokens after expiry/consumption/revocation according to configured retention. Runtime revokes rather than deletes them. Cleanup retains durable security-event evidence in audit history. Audit retention/deletion requires a separate documented maintenance policy; no automatic staff or clinical deletion is introduced.

## Verification required before marking v0.1 complete

- Check every declared constraint, trigger, FK and database privilege against real PostgreSQL.
- Verify repeat bootstrap, rollback after injected failure, repeat migrations and checksum drift.
- Verify invited/disabled/forced-change behavior and session invalidation after security changes.
- Race token issuance/redemption and final-admin removal; assert one token consumer and a surviving usable admin.
- Verify authorization is rechecked under locks and audits roll back with failed mutations.
- Verify stale row_version updates fail, expiries never revive sessions and secrets are absent from logs.
- Prove two installations cannot share session access, database credentials or files.

This document finalizes design; it does not claim any of these checks have passed. Track implementation in the [MVP checklist](../MVP-CHECKLIST.md).

# v0.2 schema — Patients, ordering and samples

**Status:** Implementation design; not migrated or tested. Applies after [v0.1](V0.1.md). Use the [shared notation](../DATABASE-SCHEMA.md#schema-notation).

## Tables and columns

Every table below has an application-generated `id uuid PK` except number_counters. **M** adds created_at, updated_at and row_version; **I** adds created_at only. All timestamps are timestamptz. Columns are required unless suffixed **?**. References imply FK with restrictive deletion.

## Constraints and limits

- Codes: trimmed uppercase ASCII, 1–40 characters, matching ^[A-Z0-9][A-Z0-9._-]{0,39}$. Names: 1–200; patient name: 1–200; phone: at most 40; address/description/reasons: at most 1000. Business numbers: at most 40. Currency: uppercase three letters and supported by the application.
- UNIQUE (test_id, code) and (test_id, position) on test_parameters; UNIQUE (parameter_id, code) and (parameter_id, position) on parameter_choices; UNIQUE (panel_id, test_id) and (panel_id, position) on panel_items.
- UNIQUE (order_id, position) on order_items; UNIQUE (order_item_id, source_parameter_id), (order_item_id, code) and (order_item_id, position) on order_parameters; UNIQUE (sample_id, order_item_id) on sample_items.
- Numeric parameters require decimal_places between 0 and 8. Other types require NULL. Choice definitions exist only for choice parameters, checked by catalog transaction services. Each active choice parameter needs at least one active choice before ordering.
- Patients: birth_date_estimated implies non-null date_of_birth. Validate date_of_birth is not in the future in the application on write; do not use time-dependent CHECK constraints. Unknown birth dates remain NULL.
- Ranges: min/max ages are nonnegative, max_age_days > min_age_days when both exist; low_value <= high_value when both exist. At least a numeric bound or nonempty display_text is required. Text/choice ranges carry no numeric bounds. Null age ends mean unbounded; ages are [min,max), numeric bounds are inclusive.
- Cancelled orders/items require all three cancellation columns; open/booked rows require those columns NULL.
- Panel id and panel snapshot are both NULL or both present. JSON values have object/array type CHECKs; exact keys and value types are validated by server contracts.
- replaces_sample_id cannot equal id and is UNIQUE when present, forming a single replacement chain. Replacement must reference an already rejected sample in the same order with the same specimen type. Enforce this cross-row rule under locks; chains cannot cycle because only existing rejected ancestors can be replaced.

## Snapshots and price rules

An order is booked atomically with one or more items and their parameter snapshots. An item represents one test occurrence, quantity one. The same test may be ordered twice as separate items. Panels expand into individual test items; the MVP panel price is the sum of member test prices, without an independent package price.

patient_snapshot contains patient_number, full_name, date_of_birth (ISO date or null), birth_date_estimated and reference_sex. It freezes the identity used for the order; patient master corrections do not silently change it. An authorized correction before any result submission updates the snapshot with audit. After submission, follow the report correction workflow rather than rewriting historical evidence.

panel_snapshot contains code and name. order_parameters copy type, required flag, unit and precision. choices_snapshot contains [{code,label}]. ranges_snapshot contains [{source_id,reference_sex,min_age_days,max_age_days,low_value,high_value,display_text}], using decimal strings for numeric bounds. Arrays may be empty where applicable; an ordered choice parameter must have choices.

Lock selected catalog rows during booking and snapshot them in one transaction. Catalog writes lock their owning test first; range/choice edits use the same owner lock. Panel booking locks panels and member tests in UUID order; panel edits use that lock order. Never mix catalog revisions within an order.

Booked price/definition snapshots are immutable. Changes require cancellation and a new item, preserving old rows. An item cannot be added/cancelled after result submission; after invoicing, apply financial adjustments separately, never silently rewrite the issued invoice. Billable order total is the sum of noncancelled item unit_price values. v0.4 freezes this into invoice lines.

## Samples and workflow

Transitions: pending → collected → received → processing → completed. Collected/received/processing may become rejected with a reason. Rejected/completed are terminal. Recollection inserts a new pending sample with a replacement link; it never rewrites rejected history. Each transition creates sample_events and an audit in the same transaction; a creation event has from_status NULL and to_status pending. CHECK event statuses against this vocabulary; reasons are required for rejection.

Lock the order, its items and then samples (each group in UUID order). sample_items must connect an item and sample in the same order with matching specimen_type_id. Verify via transaction service/constraint trigger, not just a frontend check. One sample may serve several items; an item may reference several samples. Do not link new work to rejected samples. Existing links remain for history.

One open order can have pending and completed work simultaneously. Operational completion is derived from uncancelled items, samples and approved/released results, not the orders.status field. Cancellation is permitted only before result submission, with a reason; whole-order cancellation also cancels remaining booked items. Receiving/processing cancelled work is rejected. Events retain actual collection/receipt actors and times; reject future or chronologically inconsistent event times in the service.

## Patients, numbering and indexes

patient_changes contains only changed clinical/contact fields with before/after values and reason, recorded atomically with the update. It is protected clinical data, unlike general audit metadata, and is append-only. No automatic patient merge or deletion is included; warn on possible duplicate name/birth date/phone and require staff judgment.

Allocate numbers by locking/upserting number_counters and incrementing atomically. Use installation-local formats PAT-00000001, ORD-00000001 and SMP-00000001; never reset counters in the MVP. Formatting pads to a minimum of eight digits and expands if needed. Keys are patient/order/sample with period all. Gaps are acceptable; collisions are not.

Add indexes beyond PK/UNIQUE:
- patients: (lower(full_name), id), (phone), (created_at DESC,id DESC). Name search uses a normalized prefix; broader search can be added after measuring.
- patient_changes: (patient_id,created_at DESC,id DESC); tests: (specimen_type_id); test_parameters/choices/ranges/panel_items: indexes starting with their parent FK when no existing UNIQUE index covers it; panel_items additionally (test_id).
- orders: (patient_id,ordered_at DESC,id DESC), (status,ordered_at DESC,id DESC).
- order_items: (test_id), (panel_id), (specimen_type_id); order_parameters: (source_parameter_id).
- samples: (order_id), (specimen_type_id), (status,created_at,id); sample_items: (order_item_id); sample_events: (sample_id,occurred_at,id).
- Add simple indexes for uncovered staff/actor FKs for operational joins; do not duplicate indexes already covering the leading columns.

Runtime cannot delete patients, orders, snapshots, samples or events. Catalog entries deactivate; administrative panel composition may be changed without altering booked snapshots. Readiness for v0.2 requires validated migrations and synthetic booking/recollection tests, not a populated clinical catalog.

# v0.4 schema — Invoices and payments

**Status:** Implementation design; not migrated or tested. Extends [v0.3](V0.3.md). Uses [shared notation](../DATABASE-SCHEMA.md#schema-notation).

## Tables and columns

| Table | Base | Columns beyond id/base |
| --- | --- | --- |
| user_permissions | I | user_id uuid → users; permission text CHECK IN (discount, invoice_adjust, refund, payment_reverse); granted_by uuid → users |
| invoices | M | invoice_number text UNIQUE; order_id uuid UNIQUE → orders; currency_code text; patient_snapshot jsonb object; lab_snapshot jsonb object; status text DEFAULT 'issued' CHECK IN (issued, void); issued_at timestamptz; issued_by uuid → users; subtotal numeric(14,2); discount_total numeric(14,2); total numeric(14,2); voided_at timestamptz?; voided_by uuid? → users; void_reason text? |
| invoice_items | I | invoice_id uuid → invoices; order_item_id uuid UNIQUE → order_items; position integer CHECK >= 0; description text; quantity integer DEFAULT 1 CHECK = 1; unit_price numeric(14,2); discount_amount numeric(14,2) DEFAULT 0; discount_reason text?; line_total numeric(14,2) |
| invoice_adjustments | I | invoice_id uuid → invoices; kind text CHECK IN (debit, credit); amount numeric(14,2) CHECK > 0; reason text; recorded_by uuid → users; reverses_adjustment_id uuid? UNIQUE → invoice_adjustments |
| payments | I | invoice_id uuid → invoices; amount numeric(14,2) CHECK > 0; method text CHECK IN (cash, bank_transfer, card, other); external_reference text?; received_at timestamptz; recorded_by uuid → users |
| payment_returns | I | payment_id uuid → payments; kind text CHECK IN (refund, reversal); amount numeric(14,2) CHECK > 0; reason text; method text CHECK IN (cash, bank_transfer, card, other); external_reference text?; occurred_at timestamptz; recorded_by uuid → users |
| receipts | I | receipt_number text UNIQUE; payment_id uuid? UNIQUE → payments; return_id uuid? UNIQUE → payment_returns; content_snapshot jsonb object; issued_by uuid → users |
| idempotency_records | I | actor_id uuid → users; request_key text; operation text; request_hash bytea CHECK octet_length = 32; resource_type text; resource_id uuid |

Every table has uuid PK. Codes/numbers max 40; request_key 1–128; operation/resource_type max 100; description/reasons max 1000; external_reference max 200. All monetary fields are finite. Nonnegative subtotal/discount_total/total/unit_price/discount_amount/line_total; total=subtotal-discount_total, line_total=unit_price-discount_amount and discount_amount<=unit_price. Positive discount requires reason. Currency matches three uppercase letters and the order currency.

## Constraints, history and calculations

- UNIQUE (user_id,permission); grants are additive to fixed roles and never grant clinical approval. Only lab_admin can grant/revoke them. Changes follow the foundation user-lock/auth_version/session-revocation rules. Cashier role alone does not authorize refunds or reversals.
- UNIQUE (invoice_id,position). invoice_items must belong to the invoice order and snapshot its booked prices. Lock the order/items before issuance, reject cancelled items, and require at least one line. Invoice totals must equal line sums; enforce using a deferred constraint trigger plus service calculations.
- Issued invoice lines and base totals are immutable. All later charges/credits use invoice_adjustments. Description/lab/patient snapshots are frozen at issuance. No deletes or silent edits of payments, returns or adjustments.
- Adjustment reversal creates an opposite-kind entry of equal amount pointing to the original adjustment on the same invoice. Reject double reversal and reversal-of-reversal chains. General new adjustments need reason/permission; cumulative adjusted total cannot become negative.
- receipts must reference exactly one payment or return. Each payment/return receives exactly one receipt in the same business transaction. content_snapshot stores schema_version=1, lab identity, patient identity, invoice/receipt numbers, amount, currency, method, event time, recording staff, transaction kind and balance at issuance. Stored receipt data remains valid if PDF rendering fails; render from snapshot and print. Optional persisted receipt PDFs use stored_files and require a later additive FK migration, not an undocumented column.
- Void requires no payments, returns or adjustments and all void columns; issued requires them NULL. Voiding requires invoice_adjust permission and reason. A void invoice contributes zero due and accepts no new financial entries.
- Keep received_at/occurred_at separately from created_at. Reject future event timestamps; display local business dates through lab timezone.

For an issued invoice:
- adjusted_total = total + SUM(debit adjustments) - SUM(credit adjustments).
- net_paid = SUM(payments) - SUM(payment_returns).
- outstanding = max(adjusted_total - net_paid, 0).
- refund_due = max(net_paid - adjusted_total, 0).

Derive these in queries/views, not independently editable balance columns. A credit may create refund_due on a paid invoice. New payment must be <= outstanding. A refund must be <= refund_due and <= the unreturned amount of its original payment. A reversal corrects a wrongly recorded payment, is bounded by its unreturned amount, and may reopen outstanding debt. For every payment, cumulative returns cannot exceed its amount. Refunds never also decrement the invoice total; the credit adjustment already does that.

## Atomic financial actions

Use exact decimal arithmetic end-to-end; JSON transports amounts as decimal strings. The MVP uses two fractional currency digits; reject unsupported currency precision at setup. Reject extra fractional digits before database numeric coercion and round only explicitly defined calculations. No tax engine, percentage discount stacking or exchange-rate accounting is included. Discounts are explicit per-line amounts.

Lock order first when needed, then invoice, then payment/adjustment rows in UUID order. Foundation actor authorization locks precede these. Every financial mutation locks its invoice before reading balances; this serializes concurrent payments, credits and returns. Compute totals, write the record/receipt and audit in one transaction.

Require idempotency keys for issuance, payment, adjustment, refund and reversal. UNIQUE (actor_id,request_key) in idempotency_records. Acquire a transaction-scoped advisory lock derived from actor/key before other locks; all entry points follow the same order. Recheck the caller's permission, compare operation/request_hash (canonical validated request), and return the existing resource on exact replay; mismatched reuse returns conflict. Execute the action and insert its completed record in the same transaction. Do not commit an in-progress idempotency record. Do not expire records during the MVP. A hash-lock collision only serializes unrelated requests; the exact unique key remains authoritative.

Issue invoice/receipt numbers from number_counters with kind invoice/receipt and period all, formats INV-00000001 and RCT-00000001. Do not use max(number)+1. Counter locks are acquired last, consistently, after business locks.

## Indexes and verification

Add invoice (issued_at DESC,id DESC); invoice_adjustments (invoice_id,created_at,id); payments (invoice_id,received_at,id), (received_at,id); payment_returns (payment_id,occurred_at,id), (occurred_at,id); idempotency_records UNIQUE (actor_id,request_key); permission lookup uses its user-prefixed unique index. Add FK indexes for staff and reversed-adjustment lookup where not covered. Existing unique constraints cover invoice order, receipt transaction and invoice-item order item.

Verify line/header consistency, frozen prices, currency precision, retries after response loss, simultaneous payments, credits on paid invoices, partial refunds, reversal reopening balance, unauthorized grants and all attempts at double returns. Monthly/daily reports must distinguish gross collections, refunds/reversals and net collections instead of hiding negative cash movements.
